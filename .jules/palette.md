## 2025-02-15 - No-dependency Tab Groups & Accessible SPA Views
**Learning:** For lightweight single-page applications (SPAs) built with custom vanilla JS/CSS view toggling, simply changing styles (like `.hidden` or active states) leaves assistive tech blind to the active/inactive view state. By adding `role="tablist"` with `role="tab"` on the buttons and `role="tabpanel"` on the views, we explicitly link navigation triggers with content sections. Dynamically synchronizing the `aria-selected` attribute during tab interaction (via `tab.setAttribute("aria-selected", ...)` inside our event handlers) provides direct status updates to screen readers.
**Action:** Always structure custom tab components with explicit WAI-ARIA mapping (`role="tablist"`, `role="tab"`, `role="tabpanel"`, `aria-selected`, `aria-controls`) and synchronize state updates in the DOM click handlers, ensuring the interactive state is visible to screen readers.

## 2025-02-18 - Roving Tabindex and Arrow Key Navigation in Custom Tabs
**Learning:** In a WAI-ARIA custom tab group (`role="tablist"`), screen reader and keyboard-only users expect a roving tabindex pattern. Instead of having all tabs in the standard tab sequence, only the active tab should have `tabindex="0"`, and inactive tabs must have `tabindex="-1"`. Navigation between tabs is handled seamlessly via arrow keys (`ArrowRight`/`ArrowLeft`/`ArrowUp`/`ArrowDown`) and keyboard shortcuts (`Home`/`End`), which focus and select the targeted tab, updating their active classes, aria attributes, and roving tab indexes.
**Action:** Always implement a roving tabindex pattern for custom tab components alongside arrow key and home/end shortcut navigation to meet standard accessibility patterns and keyboard-only user expectations.

## 2025-08-08 - Keyboard-Accessible Hover Tooltips for Visual Data-Viz Components
**Learning:** Custom visual components such as bar charts, graphs, or heatmaps are often interactive via mouse hover but completely inaccessible to keyboard-only and screen reader users. Assigning `tabindex="0"` to the row/bar element wrapper allows it to receive native keyboard focus. Registering `focus` and `blur` event listeners (in addition to standard `mousemove`/`mouseleave`) enables tooltips to be triggered programmatically, and using `.getBoundingClientRect()` allows the tooltip to be positioned consistently underneath the focused element without relying on mouse coordinate inputs.
**Action:** Make custom visual or data-viz components focusable via `tabindex="0"`, attach `focus`/`blur` event handlers to show and hide descriptive tooltips, and use relative DOM positioning or bounding box queries (`getBoundingClientRect()`) to render the tooltips programmatically when focused.
