# Wash Trade Detection System

A professional, production‑grade tool for auditing blockchains for wash trading and fake volume generated by bots.
Supports **20+ blockchains** and **major DEXes** (Uniswap V2/V3, PancakeSwap, Sushiswap, Curve, Balancer, TraderJoe, QuickSwap, Velodrome, Aerodrome, SyncSwap, and more).

## Features

- **Multi‑chain & Multi‑DEX** – instant support for Ethereum, BSC, Polygon, Arbitrum, Optimism, Base, Avalanche, Fantom, Celo, Gnosis, Moonbeam, Aurora, Harmony, Cronos, Metis, Boba, zkSync Era, Polygon zkEVM, Linea, Scroll, Mantle, Kava, Klaytn.
- **Measured detection** – every detector is benchmarked on real Ethereum pools and labelled wash campaigns, and CI fails if one regresses ([docs/benchmarks.md](docs/benchmarks.md)). On 27,385 honest trades from the most liquid USDC/USDT–WETH pools, the audit labels 0.07% as wash (the Phase 1 rules labelled 78.9%), while finding 86% of the injected wash trades.
  - Trades are attributed to the **transaction sender** (`tx_from`), not to the router or bot contract named in the swap event
  - **Round trips** (A‑A wash trading, after Chainalysis's heuristic 1): a trader buying and selling back the same value within 50 blocks
  - **Position neutrality** (Victor & Weintraud, WWW '21; Gan et al., ACM TOIT 2024) – a trader, or a funding‑linked group of traders, ending flat in every token while trading both sides
  - **Coordinated trading** (temporal motifs, after Chainalysis's heuristic 2) – wallets trading opposite sides of a pool within 3 blocks at matched values, repeatedly, as a closed group that ends flat: rings with no observable funding link
  - **MEV is not wash** – sandwich attackers' legs (multi‑front‑run sandwiches included) and atomic arbitrage are recognised by structure and taken out before detection; a public router or aggregator is never mistaken for an attacker's bot
  - **Cross‑pool** – `--related-pool` audits pools of one token pair together, so wash trading split over them is seen
  - **Evidence for every label** – each flagged trade says which detectors fired, what they saw (the partner leg, the window, the ring's members) and what each hit is worth; in the API, alerts and exports
  - **Calibrated scoring** – each detector's measured true/false‑positive rates turn a hit into P(wash), so noisy signals (repeated sizes, high frequency, volume outliers, closed clusters) inform the score but cannot label a trade on their own
  - Entity clustering by **first funder**, as Dune's wash‑trade filter does: wallets are linked to the address that first funded them, and exchanges, routers and other hubs link nobody (uses `trace_filter` or an opt‑in, capped block scan); every audit reports what it examined (`funding_clusters`)
  - **Trade‑size forensics** (Cong et al., Management Science 2023) – each audit reports the pool's share of round‑amount trades and its Benford conformity: 7.6–16.4% round and conforming in the clean pools, 0.14% and nonconforming in the FBI's NexF market
- **Compared with the field** – what this scanner takes from flashbots' mev‑inspect‑py, Sorella's brontes, Dune's spellbook and the literature, and what it does that they do not ([docs/comparison.md](docs/comparison.md)).
- **Measured performance** – a full audit of 10,000 real trades in 41 s and a re‑audit in 3 s, one RPC request per block, streamed and resumable ([docs/performance.md](docs/performance.md)).
- **Machine Learning** – Isolation Forest on 21 features incl. Benford's‑law deviation, amount roundness and hour‑of‑day entropy, with per‑pool contamination control and feature explainability.
- **Quantified Reporting** – wash volume in USD, per‑method breakdown, severity grading (`MINIMAL` → `CRITICAL`).
- **Web Panel** – built‑in dashboard at `/panel`: global statistics, per‑method wash‑volume charts, pool inspector, live monitor feed and audit controls; session‑cookie login backed by the API‑key system, dark/light theme, zero external assets.
- **REST API + WebSocket streaming** – `wash-api` serves on‑demand audits, risk reports and **live streaming detection** over websockets; hardened with hashed API‑key auth, per‑IP rate limiting and security headers (see [docs/api.md](docs/api.md)).
- **Real‑time Monitoring** – HTTP‑based listeners with circuit breaker protection.
- **Full Audit Reports** – JSON/CSV export.
- **Production‑Ready** – Retry logic, rate limiting, circuit breaker, graceful shutdown, input validation, SSL/TLS enforcement.

## Quick Start

### 1. Clone the repository

    git clone https://github.com/Yog-Sotho/Wash-Trade-Scanner.git
    cd Wash-Trade-Scanner

### 2. Install dependencies

Dependencies are installed from hash-locked files (`requirements*.txt`,
generated from `pyproject.toml` by `make lock`):

    python -m venv venv
    source venv/bin/activate  # or venv\Scripts\activate on Windows
    make install-dev          # = pip install --require-hashes -r requirements-dev.txt
                              #   + pip install --no-deps -e .

### 3. Set up environment

Copy `.env.example` to `.env` and fill in your RPC endpoints (at least one per chain you want to scan). Database configuration is **required** via separate secure parameters:

- `DATABASE_HOST`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`
- `DATABASE_SSL_MODE` defaults to `require`

See `.env.example` for full reference.

### 4. Start the database (Docker)

    docker run -d --name wash_detector_db \
      -e POSTGRES_USER=wash_user \
      -e POSTGRES_PASSWORD=wash_pass \
      -e POSTGRES_DB=wash_detector \
      -p 5432:5432 postgres:15-alpine

The schema is managed by Alembic migrations (`migrations/`): every command that
uses the database creates or upgrades it on startup. To do it explicitly:

    alembic upgrade head

A database created by an earlier release (before migrations) is adopted
automatically, keeping its data.

### 5. Run an audit

    python scripts/run_audit.py \
        --chain-id 1 \
        --pool 0xB4e16d0168e52d35CaCD2c6185b44281Ec28C9Dc \
        --start-block 18000000 \
        --end-block 19000000 \
        --export json

Set `ETH_RPC_URL` first — Ethereum has no public default endpoint. Mixed‑case
addresses must carry a valid EIP‑55 checksum (all‑lowercase is accepted). Block
ranges are limited to 10M spans maximum.

For more options:

    python scripts/run_audit.py --help

### 6. Train the ML model (optional)

    python scripts/train_model.py --chain-id 1 --pools 0x... 0x...

## Configuration

All settings are in `.env` (see `.env.example`). Important variables:

- `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD` – PostgreSQL connection parameters (async, SSL enforced)
- `DATABASE_SSL_MODE` – `require` (default), `verify-ca`, `verify-full`
- `BOT_ALLOWLIST` – comma‑separated addresses to skip in high‑frequency bot detection
- `ETH_RPC_URL`, `BSC_RPC_URL`, … – RPC endpoints per chain (placeholders rejected at startup)
- `VOLUME_ANOMALY_METHOD` – `mad` (default), `iqr`, or `zscore`
- `VOLUME_ANOMALY_THRESHOLD` – default 3.5 for MAD/IQR
- `RPC_MAX_FAILURES` / `RPC_RECOVERY_TIMEOUT` – circuit breaker configuration

Full reference: see `docs/configuration.md`.

## Detection Methodology

Every detector is measured, not asserted: the harness in `evaluation/` runs it on
real swap histories recorded from Ethereum mainnet and on labelled wash campaigns
injected into them, and [docs/benchmarks.md](docs/benchmarks.md) publishes its
precision, recall, F1, PR‑AUC and false‑positive rate on honest pools.

### Who traded

On an AMM every swap's counterparty is the pool, and the Swap event's `sender`
and `to` are usually a router or a bot contract. Detectors therefore attribute
each swap to the account that sent the transaction (`tx_from`), fetched at
ingestion. (Phase 1 compared `sender` and `to` and called a match self‑trading;
that flagged 70–79% of honest trades in liquid pools, because any contract that
swaps for itself matches.)

### Detectors

1. **Round trip** (`round_trip`): a trader buys and sells back in the same pool within `ROUND_TRIP_MAX_BLOCKS` (50) blocks at USD values within `ROUND_TRIP_VALUE_TOLERANCE` (1%), at least `ROUND_TRIP_MIN_COUNT` (2) times — Chainalysis's address‑level wash‑trading heuristic (25 blocks, 1%, 3 times), with parameters chosen on the benchmark. Legs in one block around another trader's swap are a sandwich (MEV), not wash.
2. **Position neutral** (`position_neutral`): within 1h / 24h / 7d windows, an entity — one trader, or the traders a funding cluster links — trades both sides at least 4 times while its net change in every token stays within `POSITION_NEUTRAL_MARGIN` (0.1%) of what it moved. This is Victor & Weintraud's position‑neutrality condition applied to AMM entities, as in Gan et al.
3. **Supporting signals**: repeated trade sizes, high‑frequency bot cadence, volume outliers (MAD/IQR), circular and closed‑cluster flow between swap senders and recipients, and swaps whose output goes to another wallet of the trader's funding cluster.
4. **Machine learning**: an Isolation Forest on 21 trade‑ and pool‑level features (incl. Benford deviation, amount roundness, hour‑of‑day entropy), computed in memory per pool. `wash-train` measures each model on the benchmark, stores its rates in the model file and refuses to save one no better than 2× a random ranking.

### Scoring

The benchmark measures each detector's true‑positive rate and its clean‑pool
false‑positive rate (95% upper bound), shipped in `config/detector_calibration.json`.
A hit is scored as P(wash | hit) by Bayes' rule with prior `WASH_PRIOR` (1%), and a
trade is labelled wash only if that reaches `SUSPICIOUS_ACTIVITY_THRESHOLD` (0.8).
Today `round_trip`, `position_neutral` and `coordinated_trading` are precise enough to label on their own;
the other signals raise a trade's score without labelling it. CI fails if the
shipped calibration no longer matches what the detectors measure.

### Known limits

Measured, and listed in [docs/benchmarks.md](docs/benchmarks.md): round trips
spread over more than 50 blocks are mostly missed; rings are caught when their
matched legs land within 3 blocks and 5% in value (the documented heuristic), and
a ring timed or sized more loosely is not; on the documented NexFundAI market
(the FBI sting token), whose wash trading Kaiko attributes to many co‑funded
wallets, the audit labels nothing; the Isolation Forest does no better than
random ranking on these patterns; and wash trading split across chains is not
correlated (there is no labelled cross‑chain data to measure it on).

### Reporting

Audit reports quantify wash activity, not just count it: wash volume in USD, wash‑volume ratio, a per‑method volume breakdown, and a severity grade (`MINIMAL` → `CRITICAL`) derived from the wash‑volume ratio.

## Testing

    pytest tests/ -v --cov=core --cov-report=html --cov-fail-under=80

Integration tests run a full audit end to end against a real PostgreSQL (with the
chain and price API simulated over local HTTP). They are skipped unless requested:

    pytest tests/integration --integration   # uses the DATABASE_* settings

Detection quality (no network or database needed):

    make eval        # measure every detector, regenerate docs/benchmarks.md
    make eval-check  # what CI runs: fail on a regression or a stale calibration

## Security

- Input validation via Pydantic (checksum addresses, block ranges, chain IDs)
- Circuit breaker for RPC resilience
- Database SSL/TLS enforcement
- Wrong API keys lock the client out with a doubling backoff (every route, the
  panel login, websockets); per-IP rate limiting; both shareable across
  instances through Redis
- Hash-locked dependencies; CI fails on any known vulnerability (pip-audit),
  type error (mypy), security finding (bandit) or fixable HIGH/CRITICAL image
  vulnerability (Trivy)
- See `docs/security.md` for full details

## API Server, Web Panel & Live Monitoring

Start the API (binds `127.0.0.1:8000` by default):

    wash-api

Open the dashboard at `http://127.0.0.1:8000/panel` — statistics, charts,
pool inspection, live monitoring and audit management in the browser.

Stream live detections for a pool over websocket:

    /api/v1/ws/monitor/{chain_id}/{pool_address}

Or have the server watch pools around the clock and alert a webhook, Slack or
email, no browser needed: set `MONITOR_POOLS` and a sink
([docs/alerting.md](docs/alerting.md)).

To expose the API beyond localhost you must enable authentication — generate
a key with `wash-genkey`, set `API_AUTH_ENABLED=true` and `API_KEY_HASHES`;
the server refuses to bind a public interface otherwise. Full reference:
[docs/api.md](docs/api.md).

The server serves Prometheus metrics at `/metrics` (RPC latency and errors,
circuit-breaker state, audit durations, detector hits, HTTP traffic), gives
every request an `X-Request-ID` that follows it into the logs, and can export
OpenTelemetry traces. Set `LOG_FORMAT=json` for one JSON object per log line.
See [docs/observability.md](docs/observability.md).

## Docker

The image (`Dockerfile`) is multi-stage: dependencies are installed from the
hash locks without a compiler, and the runtime image -- a digest-pinned
`python:3.11-slim`, running as a non-root user -- contains the installed
package but no pip, setuptools or build tools. Its default command is
`wash-api`, with a `HEALTHCHECK` on `/health/live`. Orchestrators should probe
`/health/live` for liveness and `/health/ready` (database and RPC reachable)
for readiness: see [docs/api.md](docs/api.md#health-probes).

    export ETH_RPC_URL=https://...                    # required
    docker compose run --rm audit wash-genkey         # once; prints a key and its hash
    export API_KEY_HASHES=<hash>
    docker compose up -d                              # API + panel on 127.0.0.1:8000
    docker compose run --rm audit wash-audit --chain-id 1 --pool 0x...

## Data retention

Nothing deletes data automatically. `wash-prune` counts the trades older than
`TRADE_RETENTION_DAYS` (default 90) and deletes them only with `--yes`:

    wash-prune                  # report
    wash-prune --days 30 --yes  # delete

## Export & Reporting

Use `--export json` or `--export csv` to save audit results. A JSON summary file and a CSV metrics file will be created.
